## Clarifications

### Session 2026-11-23

- [D-001] Q: 「用户在电脑前」按单条消息判断，还是持续到下一条飞书消息？ -> A: 持续状态。收到本机消息后进入「在电脑前」，收到下一条 `<lark-message>` 后回到「远程」。
- [D-003] Q: 调度会话在「在电脑前」状态下是否仍坚持全部派发？ -> A: 仍全部派发，调度会话不进入项目工作区。
- [D-004] Q: 用户直接在工作会话发消息时，工作会话怎样与用户交流？ -> A: 在会话正文直接回答与提问，不经 `send_report` 与用户对话。
- [D-007] Q: 工作会话怎样区分调度会话的消息与用户本机消息？ -> A: 调度会话发出的每条消息都带可识别的来源标记，包括新建会话时的首条任务；没有标记的消息视为用户本机消息。
- [D-002] Q: 调度会话在「在电脑前」状态下怎样回复用户与转达上报？ -> A: 回复用户、转达上报与失败都写在会话正文，不调用 `lark_notify`。
- [D-005] Q: 工作会话与本机用户交流后，任务进展与结果是否仍上报调度会话？ -> A: 影响任务的变化仍用 `send_report` 上报，例如需求变更、完成与放弃，上报注明用户当时在电脑前；普通问答不上报。
- [D-006] Q: 工作会话在本机用户离开后怎样回到远程模式？ -> A: 收到调度会话的下一条消息即回到远程模式，之后经 `send_report` 交流。
- [D-008] Q: 一个会话判定用户在电脑前后，是否告知另一方会话？ -> A: 不告知。每个会话只按自己收到的消息判断状态。
- [D-009] Q: 调度会话的在场判断是否加程序兜底？ -> A: 是。来源切换时由程序向调度会话插入系统提醒，说明用户当前在电脑前还是远程；回复渠道仍由提示词按提醒执行。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 调度会话识别用户回到电脑前 (Priority: P1)

用户平时经飞书远程指挥调度会话。用户回到电脑前，在 Web GUI 的调度会话里直接输入消息。调度会话据此判断用户在电脑前，之后在会话正文回复与转达，直到用户再从飞书发消息。

**Why this priority**: 调度会话是用户的主要入口；回复渠道错误会让用户在电脑前收不到回复，或在飞书收到重复通知。

**Independent Test**: 先从飞书发一条任务，确认飞书收到回执；再在 Web GUI 的调度会话输入一条消息，确认回复出现在会话正文，飞书没有新通知；随后等待一份工作会话上报，确认上报转达在正文。

**Acceptance Scenarios**:

1. **Given** 调度会话处于远程状态，**When** 用户在 Web GUI 直接输入消息，**Then** 调度会话在正文回复，不调用 `lark_notify`。
2. **Given** 调度会话处于「在电脑前」状态，**When** 工作会话发来上报或失败通知，**Then** 调度会话在正文转达，不调用 `lark_notify`。
3. **Given** 调度会话处于「在电脑前」状态，**When** 用户从飞书发来消息，**Then** 调度会话回到远程状态，用 `lark_notify` 回复，之后的转达也走飞书。
4. **Given** 调度会话处于「在电脑前」状态，**When** 用户在 Web GUI 下达新任务，**Then** 调度会话照常登记并派发给工作会话。

---

### User Story 2 - 工作会话识别用户直接介入 (Priority: P2)

用户在电脑前打开某个工作会话，直接输入补充要求或提问。工作会话判断这是用户本人，在正文直接对话。影响任务的变化仍上报调度会话，并注明用户当时在电脑前。

**Why this priority**: 用户直接介入时期望即时对话；当前提示词要求所有交流走 `send_report`，回复会绕到飞书。

**Independent Test**: 派发一个任务后，在 Web GUI 打开该工作会话输入一个问题，确认答复出现在该会话正文，调度会话未收到对应上报；再在该会话改一项需求，确认调度会话收到注明用户在电脑前的上报。

**Acceptance Scenarios**:

1. **Given** 工作会话正在执行派发的任务，**When** 用户在该会话直接输入问题，**Then** 工作会话在正文回答，不调用 `send_report`。
2. **Given** 用户在工作会话直接改了需求，**When** 工作会话处理该变更，**Then** 调度会话收到一份上报，上报写明需求变更来自电脑前的用户。
3. **Given** 工作会话处于本机模式，**When** 任务完成，**Then** 工作会话在正文告知用户，并用 `send_report` 上报完成且注明用户在电脑前。
4. **Given** 工作会话处于本机模式，**When** 调度会话发来消息，**Then** 工作会话回到远程模式，之后经 `send_report` 交流。
5. **Given** 调度会话新建工作会话并发出首条任务，**When** 工作会话读到该任务，**Then** 工作会话把它识别为调度会话消息，处于远程模式。

### Edge Cases

- 飞书消息与本机消息在同一轮内先后到达时，按最后一条判断状态。
- 调度会话收到的 `<work_session_message>` 与 `<work_session_failure>` 不改变调度会话的状态。
- 上报中注明「用户在电脑前」时，调度会话照常转达，自身状态不变。
- 工作会话把调度会话经 `session_send` 发来的系统提醒视为调度会话消息。
- 用户在 Web GUI 引用一条飞书消息补充要求，仍按本机消息判断。
- 会话被压缩后，状态以压缩后上下文中最近一条用户来源消息为准；无法判断时视为远程。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `SA-调度会话` MUST 区分三类入站消息：飞书消息 `<lark-message>`、工作会话消息 `<work_session_message>` 与 `<work_session_failure>`、用户本机消息。
- **FR-002**: `SA-调度会话` 收到用户本机消息后 MUST 进入「在电脑前」状态，并保持到下一条飞书消息到达。
- **FR-003**: `SA-调度会话` 在「在电脑前」状态下 MUST 在会话正文回复用户，并在正文转达上报与失败，不调用 `lark_notify`。
- **FR-004**: `SA-调度会话` 在远程状态下 MUST 保持现有行为：经 `lark_notify` 回复与转达。
- **FR-005**: `SA-调度会话` 在两种状态下 MUST 都把全部任务派发给工作会话，自身不进入项目工作区。
- **FR-006**: 调度会话发给工作会话的每条消息 MUST 带可识别的来源标记，包括新建会话的首条任务。
- **FR-007**: `SA-任务会话` MUST 把带来源标记的消息视为调度会话消息，把没有标记的用户消息视为用户本机消息。
- **FR-008**: `SA-任务会话` 收到用户本机消息后 MUST 进入本机模式，在会话正文回答与提问。
- **FR-009**: `SA-任务会话` 在本机模式下 MUST 只把影响任务的变化用 `send_report` 上报，例如需求变更、完成与放弃，并在上报中注明用户在电脑前。
- **FR-010**: `SA-任务会话` 收到调度会话消息后 MUST 回到远程模式，经 `send_report` 交流。
- **FR-011**: 两个会话 MUST 只依据各自收到的消息判断状态，不互相告知状态。
- **FR-012**: `SA-调度会话` MUST 在用户状态切换时收到程序的系统提醒，提醒写明用户当前在电脑前还是已回到远程。
- **FR-013**: 提示词与相关文档 MUST 同步描述上述行为。

### Key Entities

- **用户状态**：会话对用户是否在电脑前的判断，取值为「远程」与「在电脑前」，默认「远程」。
- **入站消息来源**：调度会话收到飞书、工作会话、用户本机三类；工作会话收到调度会话、用户本机两类。
- **来源标记**：调度会话发往工作会话的消息上可识别的标识，具体形式在计划阶段确定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 实机测试中，用户在调度会话输入本机消息后，回复与后续转达 100% 出现在正文，且飞书无对应通知。
- **SC-002**: 实机测试中，飞书消息 100% 仍经 `lark_notify` 得到回复，并使后续转达回到飞书。
- **SC-003**: 实机测试中，用户在工作会话输入的问题 100% 在该会话正文得到回答。
- **SC-004**: 实机测试中，调度会话发给工作会话的消息 100% 被识别为调度会话来源，包括首条任务。
- **SC-005**: 实机测试中，本机模式下的需求变更与完成 100% 上报调度会话，且上报注明用户在电脑前。

## Assumptions

- 用户本机消息指用户在 Web GUI 直接输入并发送的消息。
- `lark-bridge` 的飞书消息始终以 `<lark-message>` 块注入；它的提醒已要求其他来源的消息按普通方式回复。
- 两个预设的工具集保持不变，仍不含 `ask_user_question`。
- 状态判断依赖模型遵守提示词；调度会话在状态切换时另收到程序的系统提醒。
